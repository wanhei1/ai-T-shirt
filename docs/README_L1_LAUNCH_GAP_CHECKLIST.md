# L1 上线缺口清单（两种产品 + AI 定制）

适用场景：小体量可收费上线，不追求大厂级分布式复杂度。
目标：先做到“稳定赚钱 + 失败可控 + 数据不丢”。

## 1. 当前结论（可直接用于决策）

当前系统已经接近可收费上线。

- 已有：异步队列、重试退避、限流、基础告警、管理员权限、生产环境密钥强度守卫。
- 当前状态：P0/P1 核心上线项已落地，当前以稳定运行和参数调优为主。

## 2. 已达标项（可先不改）

1. 队列重试与背压：已实现。
2. 核心告警（5xx、队列等待、依赖可用性）：已实现。
3. 生产环境弱密钥拦截：已实现。
4. 管理员接口权限控制：已实现。

## 3. 必须修改项（L1 上线前）

## P0（必须先做）

1. 订单幂等
- 问题：重复请求可能重复创建订单。
- 目标：同一业务请求最多只落一笔订单。
- 建议改造：
  - 新增幂等键表（例如 `order_idempotency_keys`），`idempotency_key` 唯一。
  - 在创建订单和购物车结算接口支持 `Idempotency-Key`。
  - 命中幂等键时直接返回已创建订单，不重复扣费。

2. AI 一键降级开关
- 问题：缺少全局开关，故障时无法快速切“只卖模板款”。
- 目标：5 秒内通过环境变量或配置切换 AI 关闭。
- 建议改造：
  - 增加 `AI_ENABLED`（默认 `true`）。
  - `AI_ENABLED=false` 时，`/jobs` 的 AI/试衣入口直接返回业务友好错误码与文案。

## P1（建议 1 周内）

3. 账务一致性与对账告警
- 问题：缺少“支付成功但订单失败/未同步”的专用巡检和告警。
- 目标：每天至少一次自动对账，发现不一致自动报警。
- 当前状态：已实现（每日自动任务 + 指标上报 + Prometheus 告警）。
- 建议改造：
  - 增加对账脚本：支付流水 vs 订单 vs 会员交易。
  - 新增告警规则：不一致记录数 > 0 持续 N 分钟告警。

4. 每日自动备份执行器
- 问题：已有 DR 演练脚本，但缺日常自动备份执行链路。
- 目标：最近 24 小时订单可恢复。
- 当前状态：已实现（每日定时备份 + 备份日志 + 最近一次恢复可读性验证结果）。
- 建议改造：
  - 增加定时任务（cron/GitHub Actions/云托管）执行备份。
  - 每日产出备份日志和最近一次恢复验证结果。

5. 输入校验收紧
- 问题：关键接口仍以手写 if 判断为主，易漏规则。
- 目标：订单/支付/地址等输入可统一校验并返回一致错误。
- 当前状态：已实现（订单创建/购物车结算/会员开通统一 schema 校验，错误码与错误明细格式统一）。
- 错误码字典：已统一为前端友好字段级 code（例如 `INVALID_ADDRESS`、`INVALID_PLAN_ID`、`INVALID_ITEMS`），并可在管理端与客户端做精确提示。
- 建议改造：
  - 为订单创建、购物车结算、会员开通请求引入统一 schema 校验。

6. 预算级成本护栏
- 问题：已有速率限流，但缺“预算/日配额”控制。
- 目标：防止 AI 成本突增。
- 当前状态：已实现（用户日额度 + 全站日预算 + 超限降级/延迟/暂停模式，覆盖 AI 生成与试穿入口）。
- 建议改造：
  - 每用户每日生成额度。
  - 全站每日 AI 调用预算上限。
  - 超限自动降级（仅模板/排队延迟/暂停 AI）。

## 4. 可延后项（当前规模不必优先）

1. 多地域容灾。
2. 数据分片。
3. 微服务拆分。
4. 深度全链路 tracing 治理。

## 5. 最短改造顺序（建议 3 天）

1. Day 1：订单幂等 + AI 开关。
2. Day 2：每日备份执行器 + 恢复验收记录。
3. Day 3：对账告警 + 日预算限额。

## 6. 目标验收标准（上线闸门）

1. 峰值并发 20-50 连续 24 小时无致命故障。
2. 下单主流程成功率 >= 97%。
3. AI 生成成功率 >= 90%（失败有补偿/回退）。
4. 故障恢复时间 <= 30 分钟（有 SOP）。
5. 每日对账：支付单、订单单、生产单可闭环。

## 7. 备注

这份清单是“可收费上线（L1）”标准，不是“大厂级最终形态”。
先上线闭环，再根据真实订单量做第二阶段扩展最稳妥。

## 8. 从现在到“标准可收费服装电商”的最短 7 天改造清单

定位：当前是“会员余额制定制商城 MVP”；7 天目标是补齐标准电商最关键两条主链：支付闭环 + 履约闭环。

### 优先级定义

- P0：不做就不建议按“标准可收费服装电商”对外承诺。
- P1：上线后 1-2 周内应补齐，降低运营与财务风险。

### 工作量定义

- S：0.5-1 人日
- M：1-2 人日
- L：2-3 人日

### Day 1（P0）支付订单模型定版 + 迁移

1. 订单支付字段补齐（L）
- 新增字段：`payment_status`、`payment_channel`、`payment_order_id`、`paid_at`、`refund_status`、`refunded_at`。
- 目标：订单状态与支付状态分离，避免“发货中但未支付”的语义混乱。

2. 支付事件表（M）
- 新增 `payment_events`（幂等 event_id 唯一）。
- 目标：保留网关回调原始事件，支持追溯和重放。

3. 验收
- 迁移可重复执行；`migration-verify` 通过。

### Day 2（P0）支付下单接口（创建支付意图）

1. 新增支付意图接口（L）
- `POST /api/payments/create-intent`。
- 入参：`orderId`、`channel`、`amount`；出参：`paymentOrderId`、`clientPayload`。

2. 订单创建联动（M）
- 下单后进入 `payment_status='pending'`，不再直接视为已支付。

3. 验收
- 前端可拿到支付意图参数，订单列表可见“待支付”。

### Day 3（P0）支付回调与幂等确认

1. 新增回调接口（L）
- `POST /api/payments/webhook/:channel`。
- 验签、幂等（event_id）、防重放。

2. 状态机落库（M）
- 成功：`payment_status -> paid`，写入 `paid_at`。
- 失败/关闭：`payment_status -> failed/cancelled`。

3. 验收
- 同一回调重复 10 次仅生效 1 次；订单支付状态与回调一致。

### Day 4（P0）履约主链：发货与物流追踪

1. 新增发货数据表（M）
- `shipments`：`order_id`、`carrier`、`tracking_no`、`shipped_at`、`delivered_at`、`status`。

2. 管理端发货接口（M）
- `POST /api/admin/orders/:id/ship`、`PUT /api/admin/shipments/:id`。

3. 用户侧物流查询（S）
- `GET /api/orders/:id/tracking`。

4. 验收
- 管理端可录入运单；用户可看到物流状态时间线。

### Day 5（P1）退款/售后最小闭环

1. 售后申请（M）
- `POST /api/after-sales`（退款/退货/换货三类）。

2. 管理端审核（M）
- `PUT /api/admin/after-sales/:id`（approved/rejected/completed）。

3. 退款联动（M）
- 审核通过后触发退款请求，更新 `refund_status`。

4. 验收
- 一单可发起售后，审核后状态全链路可追踪。

### Day 6（P1）按单生产版：SKU/价格主数据 + 产能/排产最小化

1. 商品主数据（L）
- `products`、`product_skus`（尺码/颜色/售价、是否可售、生产时效 SLA）。

2. 产能与排产约束（M）
- 不做现货库存扣减，改为“每日可生产配额”与“排产负载”控制。
- 支付成功后占用当日或次日产能；超出配额时自动延后承诺发货时间。
- 超载保护使用事务 + 行锁，避免同时间段被重复占用。

3. 管理端 SKU/产能维护（S）
- 最少支持改价、上下架、修改 SLA、调整每日产能配额。

4. 验收
- 当日产能已满时不再承诺当日发货（自动顺延）。
- 订单记录 SKU 快照价格与承诺生产/发货时间，可追溯。

### Day 7（P0 收口）联调压测 + 上线闸门

1. 端到端场景回归（M）
- 标准链路：浏览 -> 下单 -> 支付成功 -> 发货 -> 查询物流 -> 申请售后。
- 覆盖组合（最少）：
  - 支付渠道：支付宝成功、取消、超时。
  - 履约：正常发货、延迟发货、物流状态更新。
  - 售后：退款申请通过、拒绝、重复提交幂等。
- 验收口径：
  - 主链路成功率 >= 97%。
  - 所有失败场景返回可识别错误码，且前端有可读提示。

2. 故障注入演练（M）
- 注入场景：
  - 回调重复（同一 `event_id` 重放 10 次，仅生效 1 次）。
  - 支付超时（订单保持 `payment_status='pending'`，可重试支付）。
  - 物流接口失败（可重试，不影响订单主状态一致性）。
  - 退款失败重试（失败有记录，重试可收敛到终态）。
- 验收口径：
  - 幂等、状态机、审计日志三者一致。
  - 任一故障注入后，系统在 30 分钟内恢复可服务状态。

3. 上线闸门报告（S）
- 压测要求：连续 24h，峰值并发 20-50，无致命故障。
- 必交指标：
  - 下单主流程成功率。
  - 支付回调成功率与重复回调拦截率。
  - 发货写入成功率与物流查询成功率。
  - 售后处理成功率与平均处理时长。
  - 故障恢复时长（MTTR）。
- 缺口清单：未闭环项需包含「风险等级、临时缓解、负责人、预计关闭时间」。
- Go/No-Go 判定：
  - Go：P0 缺口 = 0，关键指标达标。
  - No-Go：存在 P0 缺口或主链路成功率 < 97%。

### 7 天交付物清单（必须落盘）

1. 数据库迁移脚本 + 回滚说明。
2. 新增 API 文档（请求/响应/错误码）。
3. 管理端操作 SOP（支付异常、发货异常、退款异常）。
4. 每日对账报表新增维度：支付单-订单单-退款单-物流单关联率。
5. Go/No-Go 结论页（可直接用于上线审批）。
