# 上线总计划（单文档版）

适用对象：当前项目从“可跑”进入“可收费对外服务”的完整落地计划。
目标：用一份文档覆盖架构、部署、联调、压测、闸门与回滚。

## 1. 总体目标与判定标准

### 1.1 上线目标

1. 用户可通过 `https://www.bit810.cn` 稳定访问并完成下单主链路。
2. 后端通过 `https://api.bit810.cn` 提供受控 API 能力。
3. AI 生成能力由后端代理调用，不暴露内部推理端口。
4. 满足 Day 7 的 Go/No-Go 闸门标准后再正式放量。

### 1.2 放行标准（Go）

1. P0 缺口 = 0。
2. 主链路成功率 >= 97%。
3. MTTR <= 30 分钟。
4. 24h 压测与故障注入有可追溯证据。
5. 数据一致性检查（迁移、对账、发布守卫）全部通过。

## 2. 当前基线与关键事实

1. 代码已完成支付、履约、售后、按单生产与管理端初始化能力。
2. 域名已存在：`www.bit810.cn` 可用于前端入口。
3. 当前主要短板是上线证据链与端口收敛，不是核心业务功能缺失。
4. 主要风险：AI 相关端口（如 8188）可能被公网直接访问。

## 3. 目标架构（推荐）

### 3.1 域名与流量分层

1. `www.bit810.cn`：前端站点。
2. `api.bit810.cn`：后端 API。
3. AI 内部服务（ComfyUI 8188）：仅内网或白名单访问，不对公网开放。

### 3.2 网络与安全策略

1. 公网仅开放 80/443。
2. 关闭 8188/8189 对 `0.0.0.0/0` 的开放。
3. 前端不直连 AI 端口，统一走后端接口。
4. 后端开启鉴权、限流、审计日志与错误码一致性。

### 3.3 运维基础

1. HTTPS 证书可自动续期。
2. Nginx/网关统一反向代理。
3. 日志、指标、告警链路可观测。
4. 备份与恢复脚本可执行并有记录。

## 4. 分阶段实施计划

## Phase A（D0）云端入口收口与安全硬化

1. DNS 配置
- 新增 `api.bit810.cn` 解析到后端入口。
- 保持 `www.bit810.cn` 指向前端入口。

2. 反向代理
- 网关按 Host 转发：`www` -> 前端；`api` -> 后端。
- 全站强制 HTTPS。

3. 安全组/防火墙
- 仅开放 80/443。
- 禁止公网直接访问 8188/8189。

4. 验收
- `https://www.bit810.cn` 可访问。
- `https://api.bit810.cn/health` 可访问。
- `http://<公网IP>:8188` 访问失败（预期行为）。

## Phase B（D1-D2）配置对齐与联调

1. 环境变量对齐
- 前端 `NEXT_PUBLIC_API_URL` 指向 `https://api.bit810.cn`。
- 后端 `FRONTEND_URL` 包含 `https://www.bit810.cn`。
- AI 配置走后端代理，避免浏览器直连 8188。

2. 数据库与迁移
- 执行迁移与校验，确保 schema 完整。

3. 功能联调
- 主链路：浏览 -> 下单 -> 支付 -> 发货 -> 物流 -> 售后。
- 管理端：新增商品、新增 SKU、改价、上下架、SLA、产能配置。

4. 验收
- 主链路可走通。
- 管理端初始化能力可用。

## Phase C（D3-D4）小流量外测（5-10 人）

1. 发放测试账号和场景脚本。
2. 收集关键问题：支付、发货、售后、AI 体验、异常提示。
3. 每日收敛 P0/P1 缺陷并回归。

验收：
- P0 用户可见问题清零。
- 核心流程用户反馈可接受。

## Phase D（D5-D6）Day 7 前置演练

1. 数据一致性检查
- 迁移校验。
- 对账巡检。
- 发布守卫。

2. 故障注入预演
- 回调重复。
- 支付超时。
- 物流接口失败。
- 退款失败重试。

3. 恢复能力验证
- 记录告警触发到恢复耗时。
- 校验回滚与手工兜底 SOP。

验收：
- 每类故障均有处理记录与恢复证据。

## Phase E（D7）24h 压测与 Go/No-Go

1. 压测执行
- 并发 20-50，持续 24h。
- 记录成功率、延迟、错误率、恢复时长。

2. 闸门判定
- P0 缺口、主链路成功率、MTTR 三项硬指标。

3. 形成审批材料
- Go/No-Go 报告。
- 缺口清单（含 owner 与 ETA）。

## 5. Day 7 检查清单（执行版）

1. 端到端回归
- 浏览 -> 下单 -> 支付成功 -> 发货 -> 查物流 -> 申请售后。

2. 故障注入
- 同一 `event_id` 重放 10 次仅生效 1 次。
- 支付超时后订单保持 pending 且可重试。
- 物流失败可重试且不破坏主状态一致性。
- 退款失败可重试并收敛到终态。

3. 指标采集
- 下单主流程成功率。
- 支付回调成功率。
- 重复回调拦截率。
- 发货写入与物流查询成功率。
- 售后处理成功率。
- MTTR。

4. 证据落盘
- 压测结果：`artifacts/perf/<timestamp>/`
- 对账结果：`artifacts/reconciliation/`
- Go/No-Go 报告：`docs/GO_NO_GO_REPORT_FILLABLE.md`

## 6. 命令执行清单（建议顺序）

1. 构建与迁移
- `npm run build`
- `npm run migrate:verify`

2. 上线守卫
- `npm run release:guard`
- `npm run dr:readiness`
- `npm run billing:reconcile`

3. 压测与故障注入
- `npm run perf:capacity-suite`
- `npm run perf:dependency-chaos`

## 7. 风险与缓解

1. 风险：AI 端口暴露导致滥用与攻击。
- 缓解：关闭公网 8188；仅后端可访问。

2. 风险：发布守卫缺失关键环境变量。
- 缓解：补齐变量后纳入发布前置检查。

3. 风险：缺少 24h 压测证据导致结论不可采信。
- 缓解：必须在云端环境跑满 24h 并保存产物。

4. 风险：故障演练不足导致真实故障恢复不可控。
- 缓解：按注入清单逐项演练并签字确认。

## 8. 角色分工

1. 技术负责人
- 主导架构收口、闸门判定、最终放行。

2. 后端负责人
- 支付/履约/售后/对账链路稳定性与指标达标。

3. 前端负责人
- 用户链路可用性、错误提示一致性、管理端可运维。

4. 运维负责人
- 域名、证书、网关、端口策略、监控告警、备份恢复。

5. 运营/测试负责人
- 外测组织、问题收集、回归验收与发布确认。

## 9. 回滚与应急预案

1. 回滚触发条件
- 主链路成功率明显低于阈值。
- 支付/订单状态出现持续不一致。
- AI 服务异常导致全站核心功能不可用。

2. 回滚动作
- 回退到上一个稳定 tag。
- 暂停 AI 高风险入口（保留模板售卖）。
- 启用手工订单处理与客服兜底话术。

3. 事后复盘
- 根因、时间线、影响面、修复项、预防项。

## 10. 最终发布流程（简版）

1. 完成 Phase A-D。
2. 执行 Day 7 全量检查。
3. 更新 Go/No-Go 文档并完成签审。
4. 结论为 Go 后再正式放量。
5. 上线后 24 小时进入强化值班。
